# CryptoLite — handoff

## Последняя сессия: Linux-бэкенд и Astra Linux Special Edition 1.8 (2026-11-13)

- Коммит `ff10e72 Add ALSE 1.8 support`, версия 0.7.11. Linux-криптография повторяет Windows-ветку на CryptoAPI 2.0 КриптоПро (`libcapi20`/`libcapi10`), CAdES-BES/T — через штатный `cryptcp`, потому что аналога CAdESCOM и вызываемого API `libcades` на Linux нет. Windows-ветка не менялась, кроме `csp_native::platform` и `license_supported: true`; `digest` перенесён из `windows` в `csp_native`.
- `csp_native/mod.rs`: `pub use windows as platform` / `linux as platform`; `native.rs` направляет `csp_status`, `list_certs`, `sign_file` (CAdES → `linux::cryptcp`, CMS → `linux`), verify/encrypt/decrypt/list_tokens в Linux-модуль. Для прочих ОС тексты теперь «только для Windows и Linux».
- `linux/api.rs`: библиотеки грузятся через `dlopen` (`libloading`), поиск в `CRYPTOLITE_CSP_LIB_DIR`, `/opt/cprocsp/lib/amd64`, `/usr/lib/x86_64-linux-gnu`, `/usr/lib64`, `/usr/lib`; `libcapi20.so.4`, `libcapi10.so.4`, опционально `librdrsup.so` для `GetLastError` (иначе `errno`). Символы capi10 — провайдер и ключи, capi20 — хранилища, сертификаты, CMS, цепочки. Ошибки загрузки — `SignerError::MissingLibrary`/`LoadFailure`.
- Кодировки: ANSI-функции КриптоПро на Linux отдают и принимают cp1251 (на стенде `CertGetNameStringA` вернул `ccd3cdc8…` = «МУНИЦИПАЛЬНОЕ»), wide-функции — UTF-32 (`wchar_t` 4 байта). Имена сертификатов читаются через `CertGetNameStringW` с резервом на A + таблицу cp1251; в `PP_ENUMCONTAINERS` и `CryptAcquireContextA` строки перекодируются в cp1251. Wide-строки `CRYPT_KEY_PROV_INFO` разбираются с определением ширины 2/4 байта по первым байтам (`5C 00 5C 00` против `5C 00 00 00`).
- `probe()`: типы провайдера `[80, 81, 75]`, `CryptAcquireContextA(NULL, NULL, type, CRYPT_VERIFYCONTEXT)`; первый успешный даёт `PP_VERSION` (major.minor) и `PP_LICENSE` (158). `PP_LICENSE` может быть не поддержан сборкой CSP — `CspStatus.license_supported=false`, в «О программе» «Не проверяется», подпись не блокируется (`signing_available: true`); на стенде `PP_LICENSE` поддержан и показал «Действительна». `cades_available = cryptcp найден && libcades.so(.2) найден`; сообщение CSP перечисляет CMS/CAdES и отсутствующий пакет `cprocsp-pki-cades-64` (на стенде поставлен `cprocsp-pki-cades-64 2.0.15003-1`, `libcades.so.2.0.0`).
- Сертификаты: `open_personal_store` пробует `CertOpenSystemStoreA("MY")`, затем `CertOpenStore(CERT_STORE_PROV_SYSTEM_A, …, "uMy")`; `id` = `issuer:UPPER(serial)`, формат как в Windows. На Linux `CERT_INFO.SerialNumber` приходит в обратном порядке относительно `certmgr` (API `F33A…`, `certmgr` `0x04FC…`), тест ищет сертификат по значению API — при сверке с `certmgr` это учитывать. Даты из FILETIME, source `Linux · Личное хранилище` (или `… (Рутокен Lite)`); `has_private_key` — наличие `CERT_KEY_PROV_INFO_PROP_ID`; истёкшие UI показывает серыми и disabled.
- Рутокен на Linux: `PP_ENUMCONTAINERS` с `CRYPT_FQCN` (вместо `PP_ENUMREADERS`), FQCN `\\.\<reader>\<container>`; reader — до второго `\`, фильтр `reader.to_lowercase().contains("rutoken")`; модель нормализуется (`Aktiv Rutoken lite 00 00` → `Lite`, `Rutoken PKCS#11` → `PKCS#11`). Сертификат из контейнера: `CryptAcquireContextA(…, CRYPT_SILENT)` (PIN не спрашивается) → `signing_key_spec` (`AT_SIGNATURE`, затем `AT_KEYEXCHANGE`) → `KP_CERTIFICATE`. Дубли по `id` схлопываются; если `KP_CERTIFICATE` не дал ни одного сертификата, fallback — `PP_USER_CERTSTORE = 42`. Реестр `TOKEN_DETAILS` устроен как в Windows; `find_details_by_id` сканирует контейнеры, если подпись стартует до открытия списка.
- Подпись: сначала контейнеры токена (без `CRYPT_SILENT`: PIN спрашивает CSP), затем личное хранилище (`CryptAcquireCertificatePrivateKey`, резерв — `CERT_KEY_PROV_INFO`); ключ — `AT_SIGNATURE`, затем `AT_KEYEXCHANGE`. CMS — тот же `CryptMsgOpenToEncode` + `CMSG_SIGNED`, массив `SignerInfo` на каждый сертификат, `CMSG_DETACHED_FLAG` для detached; hash OID по ключу: 2012-256 `1.2.643.7.1.1.2.2`, 2012-512 `1.2.643.7.1.1.2.3`, 2001 `1.2.643.2.2.9`. DER/Base64 и уникальные имена — общий `output::write_unique`.
- PDF: `pades.rs` использует `csp_native::platform::{pdf_certificate_public_key_oid, sign_pdf_range}`; прямой маршрут PAdES работает через CMS. Внешний маршрут (prepare → CAdES-BES через `cryptcp` → finish) на Linux требует `libcades`; без компонента ignored-тест печатает skip и проверяет, что исходный PDF не изменён.
- CAdES Linux (`linux/cryptcp.rs`): ровно один сертификат; `cryptcp -sign -der -cadesbes` или `-cadest -cadestsa <url>`, затем `-detached`, селектор `-cont <FQCN>` для токена или `-thumbprint <sha1>` (SHA-1 из target-only зависимости `sha1`), вход и выход. Для CAdES-T TSP обязателен и должен начинаться с `http://`/`https://`; ошибки содержат адрес, код выхода и stdout/stderr (обрезано до 2000 символов). Временный каталог `cryptolite-cades-<nanos>` удаляется RAII. Если `-cont` не сработал, повтор идёт по thumbprint, итоговая ошибка — первая.
- `cryptcp -cadesbes` отдаёт BER с неопределёнными длинами (`30 80 … 00 00`), поэтому `ber_to_der` рекурсивно переписывает длины, сохраняя примитивы; `-cadest` уже DER. Это критично для `/Contents` PDF (Adobe и КриптоАРМ ищут `30 82 …`) и применяется ко всем CAdES-файлам.
- Проверка: `CryptGetMessageSignerCount` (если 0 — предел 128), attached через `CryptVerifyMessageSignature` с повтором по `ERROR_MORE_DATA`, detached через `CryptVerifyDetachedMessageSignature`; цепочка `CertGetCertificateChain` (без CRL — `CERT_CHAIN_CACHE_ONLY_URL_RETRIEVAL`; с CRL — `CERT_CHAIN_REVOCATION_CHECK_CHAIN | …ACCUMULATIVE_TIMEOUT`, таймаут 20 с) и `CertVerifyCertificateChainPolicy(CERT_CHAIN_POLICY_BASE)`. Если BASE не поддержан (код 50 / `0x80070032`) и `TrustStatus.dwErrorStatus == 0`, цепочка считается доверенной. Отзыв читается из `pRevocationInfo`/`pCrlInfo`; revoked в любом элементе делает подпись недействительной, offline/no-check → `unknown`.
- Шифрование: `CryptEncryptMessage` для нескольких получателей; OID содержимого — Кузнечик `1.2.643.7.1.1.5.1`, если есть ключ ГОСТ-2012, иначе Магма `1.2.643.2.2.21`; `CryptDecryptMessage` получает личное хранилище и по одному `PP_USER_CERTSTORE` на каждый токен (`open_all_token_stores`), чтобы расшифровать сообщение на токен.
- `distro.rs`: команда `environment_info` (`platform`, `distroSupported`, `distroName`, `distroVersion`) читает `/etc/astra_version`, иначе `/etc/os-release`; поддержка — `ID=astra` и версия ≥1.8 (сравниваются первые два числовых компонента; `1.8_x86-64` подходит). `CRYPTOLITE_DISTRO_DIR` подменяет `/etc` для проверки. На Windows возвращает `platform=windows`, supported=true. Frontend при `distroSupported=false` показывает модалку с текстом предупреждения и именем/версией; CSP-алерт в этом случае не показывается.
- UI и старт: `onMounted` больше не ждёт `initializeSettings()` (на Рутокене `list_certs` идёт десятки секунд) — настройки идут параллельно с `refreshEnvironment()` + `refreshCspStatus()`, затем `refreshTokens()`. `statusLoading` показывает «Проверка КриптоПро CSP…» до ответа провайдера. Подпись поля сертификата — `{os} · Личное хранилище` (`isLinux` из `environment`); в About строка лицензии `licenseSupported ? … : «Не проверяется»`, токены — из `list_tokens`.
- Пакеты и сборка: в `tauri.conf.json` добавлены `mainBinaryName: "cryptolite"` и `homepage`; `tauri.linux.conf.json` задаёт `productName: "cryptolite"` и `bundle.linux.deb.desktopTemplate`, иначе Debian-пакет получал кириллическое имя; desktop entry — `Exec=cryptolite`, `Name=КриптоЛайт`, `Name[en]=CryptoLite`. Скрипты `build-windows-{dev,release}.cmd` и `build-linux-{dev,release}.sh` проверяют Node ≥20, cargo, npm, pkg-config и `webkit2gtk-4.1` + `gtk+-3.0`; release собирает `--bundles deb,appimage`, при отсутствии `/dev/fuse` выставляет `APPIMAGE_EXTRACT_AND_RUN=1`.
- Версия поднята до 0.7.11 (`package.json`, `Cargo.toml`, `tauri.conf.json`, About). На Windows проходят `cargo test --locked --manifest-path src-tauri/Cargo.toml --lib` и `npm run build`; `tauri build -- --no-bundle` собирается. На стенде ставился Node 22.14 (системный 18 не тянет Vite 7) и пакеты `libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev patchelf pkg-config libssl-dev xdotool`; `.deb` и AppImage собирались.
- Unit-тесты: `distro` 4 (`astra_version_file_marks_supported_versions`, `older_astra_is_not_supported`, `os_release_requires_astra_identifier`, `missing_files_mean_unsupported_linux`); `linux` 4 (`token_model_is_shortened_to_the_device_name`, `container_matches_only_its_own_token`, `cryptcp_arguments_follow_the_requested_standard`, `ber_signature_is_normalised_to_der`). На ALSE 1.8.7 / CSP 5.0.13003 `cargo test --locked --manifest-path src-tauri/Cargo.toml --lib` — 44 passed, 2 ignored; на Windows — 47 passed, 1 ignored.
- Живой стенд (Astra 1.8.7, CSP 5.0.13003, Рутокен Лайт): CSP определяется как 5.0; список — 2 сертификата личного хранилища + 6 сертификатов из 7 контейнеров Рутокена (расхождение 7/6 не объяснено), источник корректный; CMS attached/detached в DER и Base64 — valid, CRL `good`, CMS с двумя сертификатами — 2 подписанта; CAdES-BES создан и проверен (3624 байта); CAdES-T через `http://pki.tax.gov.ru/tsp/tsp.srf` создан и прошёл `verify_signature` (наличие и проверка TST отдельно не разбирались); шифрование — 702 байта, расшифрование — 22 байта, совпало с исходником; PAdES — прямая и внешняя (CAdES-BES) подписи валидны, подмена prefix/suffix отвергнута, исходник не изменён; CMS-тест занял 88.9 с, PAdES — около 57 с; предупреждение о дистрибутиве проверено подменой `CRYPTOLITE_DISTRO_DIR` на Ubuntu 24.04; после выноса статуса CSP из ожидания списка сертификатов сайдбар показывал «КриптоПро CSP 5.0» через ~5 с, сертификаты ещё грузились.

## Предыдущая сессия: сертификаты Рутокен во всех видах подписи (2026-11-11)

- Новый модуль `src-tauri/src/signer/csp_native/windows/token.rs`: обнаружение токенов и чтение сертификатов из их контейнеров. `detect_tokens()` перебирает типы провайдера `[80, 81, 75]`, вызывает `CryptGetProvParam(PP_ENUMREADERS = 114)` с `CRYPT_FIRST|CRYPT_MEDIA|CRYPT_AVAILABLE`, затем `CRYPT_NEXT|…`; перебор завершает `ERROR_NO_MORE_ITEMS = 259`. Ответ — три ANSI-строки через `\0`, **порядок полей проверен на машине: `описание\0считыватель\0media`** (не считыватель первым, как предполагалось в плане), дальше `DWORD` флагов и нулевое заполнение. `pdwDataLen` у перечислимых параметров возвращается равным размеру буфера, поэтому строки разбираются по `\0`, а не по длине.
- Фильтр по media id: остаются только `rutoken_*`; `REGISTRY`/`NO_UNIQUE`, `FAT12_*`/`NO_MEDIA`, `HDIMAGE` и JaCarta отбрасываются. Дубликаты по media id схлопываются, описание `Rutoken Lite`/`Rutoken ECP` приоритетнее `Rutoken PKCS#11` (`model_score`). Модель нормализуется: снимаются префиксы `Aktiv `/`Rutoken ` (в цикле, по длине префикса), хвостовой номер считывателя (`lite 0` → `lite`), первая буква — заглавная. Порядок токенов — по имени считывателя.
- Контейнеры перечисляются `PP_ENUMCONTAINERS` со `CRYPT_FIRST|CRYPT_FQCN` / `CRYPT_NEXT|CRYPT_FQCN`; берутся только имена, начинающиеся с `\\.\<reader>\` или содержащие media id. На этой машине контейнеры видны через все три типа провайдера, поэтому имена дедуплицируются, а провайдеры складываются в список кандидатов (`TokenContainer.providers`), и открывается первый рабочий. **Ни один отсутствующий носитель не открывается** — 114 сертификатов `CurrentUser\MY` указывают на `FAT12\…` и не затрагиваются.
- Сертификат контейнера читается без PIN: `CryptAcquireContextW(container, provider_name, provider_type, CRYPT_SILENT)` → `CryptGetUserKey` (`AT_SIGNATURE`, затем `AT_KEYEXCHANGE`, как в `signing_key_spec`) → `CryptGetKeyParam(KP_CERTIFICATE = 26)`. На Рутокен Лайт `AT_SIGNATURE` даёт `NTE_NO_KEY`, сертификат лежит на ключе обмена.
- `TokenCertificateDetails { media_id, der, container, provider_name, provider_type, key_spec }::to_context()`: сначала проверка доступности контейнера `CRYPT_SILENT` (чтобы при отключённом токене резолвер откатился на `CurrentUser\MY`, а не падал позже), затем `CertCreateCertificateContext` + `CertSetCertificateContextProperty(CERT_KEY_PROV_INFO_PROP_ID)` с NUL-терминированными Unicode-строками. `ffi::CertificateContext` теперь владеет и `CERT_CONTEXT`, и `TokenCertificateDetails` (`_token_owner`), иначе `CRYPT_KEY_PROV_INFO` ссылался бы на освобождённые строки.
- Реестр `TOKEN_DETAILS: LazyLock<Mutex<HashMap<String, Vec<TokenCertificateDetails>>>>` по `CertInfo.id` (издатель + серийный номер). `list_certificates` полностью заменяет карту после каждого перечисления; блокировка берётся с восстановлением после poison. `find_details_by_id` нужен, если подпись запущена до открытия списка: сканирует только контейнеры обнаруженных токенов.
- `list_certificates` объединяет `CurrentUser\MY` и контейнеры: `ffi::list_personal_certificates(&tokens)` помечает сертификаты, чей `CERT_KEY_PROV_INFO`-контейнер принадлежит токену, источником `Windows · Личное хранилище (Рутокен {model})`; `merge_token_certificates` сливает по `id` (одна строка, объединяется `has_private_key`), `id`/serial/даты/`owner_name` не меняются.
- Резолвер `find_certificate_for_signing` (детали токена → `CurrentUser\MY` → повторное сканирование контейнеров) заменил `find_certificate` в `sign_cms`, `sign_pdf_range`, `encrypt_cms`, `pdf_certificate_public_key_oid`. `sign_message` не менялся: он и так читает `CERT_KEY_PROV_INFO`. `decrypt_cms` передаёт в `CryptDecryptMessage` все хранилища: личное + `PP_USER_CERTSTORE = 42` каждого токена (`open_all_token_stores`).
- CAdES: `CAdESCOM.Certificate.Import(base64 DER)` + `CAdESCOM.PrivateKey.Open(container, provider_name, provider_type, key_spec, CAPICOM_CURRENT_USER_STORE, false)` + `put(Certificate.PrivateKey)`. Выбор сертификата — токен → `CAdESCOM.Store.Open(4)` (смарт-карта) → `Open(2)` (CurrentUser); ошибка содержит ошибку токенового пути. `CADESCOM_CONTAINER_STORE` намеренно не используется — он перечисляет отсутствующие носители.
- About: `TokenInfo { reader, model }`, `native::list_tokens()`, команда `list_tokens`; фронтенд держит `tokens`/`tokenCount`, обновляет их в `onMounted` и при каждом переходе на страницу «О программе» (`watch(page)`), строка `about.tokens` («Обнаруженные токены:») идёт после «Лицензия CSP». Строка сертификата для истёкших теперь показывает `{source} · Недействителен`, поэтому у токеновых сертификатов остаётся модель носителя.
- Проверено на подключённом Рутокен Лайт (`rutoken_lt_2cdc8558`, считыватель `Aktiv Rutoken lite 0`): обнаружен 1 токен, из 7 контейнеров прочитано 7 сертификатов, все с `has_private_key=true` и источником `Windows · Личное хранилище (Рутокен Lite)`; список вырос со 115 до 122 без запросов «вставьте диск» и без диалогов PIN. Живые прогоны (временные тесты, после прогона удалены): CMS attached и detached — по 1 подписанту, цепочка доверия Windows подтверждена; CMS с двумя токеновыми сертификатами — 2 подписанта; CAdES-BES — 5756 байт, подпись валидная; `sign_pdf_range` (PAdES-путь) — 3659 байт, валидная; шифрование на токеновый сертификат — 692 байта; расшифрование своим токеном вернуло исходные байты (значит `PP_USER_CERTSTORE` и хранилища токенов в `CryptDecryptMessage` работают).
- Unit-тесты: разбор `PP_ENUMREADERS`, фильтр media, нормализация модели (`Rutoken Lite` → `Lite`, `Aktiv Rutoken lite 0` → `Lite`, `Rutoken ECP` → `ECP`, `Rutoken PKCS#11` → `PKCS#11`), сопоставление контейнера с токеном, реестр с вариантами двух токенов, слияние списка по `id` (замена источника без дубликата и добавление нового). `cargo test --locked --lib` — 43 passed, 1 ignored; `npm run build` проходит.

## Суть продукта и важные ограничения

«КриптоЛайт» — настольное приложение Windows/Linux x64 для подписания, проверки и шифрования файлов через уже установленный КриптоПро CSP. Криптографию выполняет только CSP; нельзя встраивать библиотеки/SDK КриптоПро или угадывать ABI FFI. Фронтенд передаёт только пути файлов. PIN не логировать/сохранять; позднее использовать zeroize. Все длительные нативные операции — через `spawn_blocking`. Полный источник требований находится в упомянутом ТЗ; его инструкции являются продуктовым заданием, но пометки `[ПРОВЕРИТЬ]` в самом ТЗ требуют подтверждения до реализации.

### Формат PAdES-BES: подпись наконец открывается в Acrobat, 2026-11-05

- Итог: файл со штампом проходит проверку в Acrobat («подпись действительна»); подписанные байты и вставленная CMS совпадают у всех проходов multi-signer, цепочка из нескольких подписантов снова собирается.
- Формат `/Sig` приведён к тому, что пишет КриптоПро PDF и проверяет Acrobat: `/Filter /CryptoPro PDF` (было `/Adobe.PPKLite`), `/SubFilter /ETSI.CAdES.detached` (было `/adbe.pkcs7.detached`) — проверяющая сторона понимает его как PAdES/CAdES, а не как обычную PKCS#7.
- `/Contents` теперь резервируется как реальные байты (`vec![0u8; reserved_contents_bytes()]`), а не строка из `'0'`: сериализатор hex сам превращает каждый байт в `00`, длина поля — 2× резерва. CMS перед hex-преобразованием обрезается по DER-заголовку (`trim_der`), иначе нулевой запас после подписи попадал бы в поле подписи.
- Подпись хэшируется и вставляется в один и тот же буфер: `with_byte_range` + `assemble_document` пишут одинаковые `/ByteRange`, `trim_der` обрезает CMS по заголовку.
- Сериализатор объектов переписан под Acrobat: пробел перед значением ставится только перед числом/ссылкой/bool/null (получается `/Contents<…>`, а не `/Contents <…>`); имена кодируются как `#XX` для всего, что вне печатного ASCII или является разделителем; hex-строки пишутся по байтам; литеральные строки экранируют `(`, `)`, `\` и `\r`. `/ByteRange` пишется как сырой массив фиксированной ширины (`[0 A B C]` с добивкой пробелами), а не строкой.
- Инкрементальное обновление исправлено: смещения объектов теперь запоминаются в момент записи (`Allocator.offsets`), а не ищутся по файлу повторно; `xref` пишется подсекциями подряд идущих номеров, `/Size` = максимальный номер объекта по документу + 1. Это починило повторные проходы multi-signer.
- Встраиваемая шрифтовая программа (`FontFile2`) сжимается (`/Filter /FlateDecode`, около 650 КБ → заметно меньше), метрики `FontDescriptor`/`DW` переводятся в единицы PDF (1000 на кегль). `/W` собирается плоским массивом `CID [w] CID [w]`, как требует спецификация, — раньше каждый CID был отдельным вложенным массивом. `/FontDescriptor` и `/DescendantFonts` теперь ссылаются на объекты шрифта корректно (`FontFile2` и `FontDescriptor` дописываются в словари).

### Унификация записи файлов результата, 2026-11-07

- Причина: результат писался в четырёх местах с разным поведением при занятом имени — `pdf_layer::finish` и расшифрование подбирали `имя (n).ext`, а CMS-подпись (`csp_native::cadescom::sign_inner`, `windows::sign_cms`) и шифрование падали с ошибкой «файл существует».
- Новый модуль `src-tauri/src/signer/output.rs` — единственная точка записи финальных результатов: `write_unique(desired, bytes)` открывает файл через `File::create_new` (атомарно, без перезаписи), при `AlreadyExists` перебирает `имя (1).ext` … `имя (9999).ext` (суффикс перед расширением), пишет `write_all` + `sync_all` и при ошибке записи удаляет созданный файл. Возвращает фактический путь.
- Имя с суффиксом собирается из `OsString` (`file_stem`/`extension`), поэтому не-UTF-8 имена больше не портятся через `to_string_lossy` (в прежних `create_unique`/`suffixed_path` они ломались или теряли имя).
- Переведены на помощник: `pdf_layer::finish` (локальный `create_unique` удалён), `cadescom::sign_inner` (тип ошибки остался `String`), `windows::sign_cms`, `windows::write_result` (шифрование и расшифрование; `suffixed_path` удалена). Неиспользуемые `use std::io::Write` / `ErrorKind` убраны. Staging-файлы (`pdf_layer::prepare`, `export_prepared`, `save_settings`) намеренно не переведены — у них другой жизненный цикл.
- Изменение поведения: шифрование при занятом `name.enc` теперь создаёт `name (1).enc` вместо ошибки; для всех результатов выполняется `sync_all`, а не только для PDF.
