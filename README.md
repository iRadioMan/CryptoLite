### Настольное приложение на Rust, Tauri 2, Vue 3, TypeScript и Tailwind CSS для подписи и шифрования файлов через установленный в системе КриптоПро CSP

## Состояние

Что работает: 
- Интерфейс подписания, проверки, шифрования, настроек и сведений о программе
- Обнаружение CryptoPro CSP на Windows
- Пакетная CMS/PKCS#7 и CAdES-BES подпись, включая параллельную multi-signer подпись несколькими сертификатами в один файл
- Проверка подписей, статус цепочки Windows (проверка цепочки использует локальный кэш Windows без сетевой проверки отзыва)
- Шифрование/расшифрование CMS EnvelopedData для нескольких получателей
- Встроенная подпись PDF (PAdES-BES) с видимой отметкой об ЭП по ГОСТ Р 7.0.97-2025: прямоугольник на каждого подписанта в предпросмотре PDF, последовательная подпись несколькими сертификатами
- Drag-and-drop
- Автоматическое сохранение пользовательских настроек

## Требования для разработки

- Rust stable и Cargo;
- Node.js 20.19+ или 22.12+;
- системные зависимости Tauri 2/WebView2 на Windows либо WebKitGTK 4.1 и build tools на Linux.

```sh
npm install
npm run tauri dev
```

Собрать frontend отдельно: `npm run build`. Создать standalone Windows exe без установщика: `npm run tauri build -- --no-bundle`. Для запускаемый из дерева проекта режим разработки: `npm run tauri dev`.

Для диагностики каталога библиотек можно задать `CPSIGNER_CSP_LIB_DIR`. На Windows приложение пробует открыть зарегистрированный CryptoPro CSP через системный CryptoAPI без доступа к контейнерам ключей. Сертификаты в первой итерации списка читаются из личного хранилища текущего пользователя. Статус CSP не означает, что операции подписи уже подключены.

### Проверка инкрементальной PDF-подписи

PDF writer сохраняет все байты исходника и тип xref (table/stream), добавляет новую
ревизию через lopdf 0.46.0 и отказывает в подписи PDF с восстановленным xref.
Оба API, `sign_pdf` и `sign_pdf_prepare` → `sign_pdf_finish`, подписывают префикс
и суффикс без `<Contents>`, с уже заполненным `ByteRange`. После успешного prepare
его staging-файл принадлежит вызывающей стороне до finish; если finish отменён,
вызывающая сторона должна удалить этот временный файл.

Структурные тесты не заменяют проверку криптографии и Acrobat. Для этого исправления
получены успешные результаты внешней проверки на Acrobat Pro DC 2022.001.20086 x64,
КриптоПро PDF 2.0.2175 и CSP 5.0.13000: оба маршрута runner дают действительные
подписи, а изменение каждого из двух подписанных сегментов отвергается.
В новых CMS обоих маршрутов проверены detached id-data, contentType, messageDigest
и signingCertificateV2 с ГОСТ-2012-256. ГОСТ-2012-512 и ГОСТ-2001 не проверены.
При последующих изменениях PDF writer или криптографического пути приёмку ниже
нужно повторить на новой сборке.

```powershell
npm ci
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib
npm run tauri build -- --no-bundle
cargo test --locked --manifest-path src-tauri/Cargo.toml --lib --no-run --message-format=json
```

Последняя команда сообщает `executable` в `compiler-artifact` для `cryptolite_lib`
с `profile.test=true`. Этот test executable можно передать как
`cryptolite-verification.exe` вместе с release exe — Rust на проверяющем ПК не нужен.
Обычный suite пропускает реальную подпись; runner запускают только явно, с разрешённым
сертификатом и закрытым ключом на ПК с лицензированным CSP и доступным CAdESCOM:

Сначала получить serial в формате backend (байты Windows CryptoAPI, little-endian).
Под тем же пользователем Windows, который запускает CryptoLite, выполнить:

```powershell
Get-ChildItem Cert:\CurrentUser\My |
    Select-Object SerialNumber,
        @{Name='SerialForRunner'; Expression={
            [BitConverter]::ToString($_.GetSerialNumber()).Replace('-', '')
        }},
        HasPrivateKey |
    Format-List
```

Команда только читает сведения о сертификатах. Найти разрешённый сертификат по
`SerialNumber`; при однозначном соответствии и `HasPrivateKey : True` скопировать
его `SerialForRunner` в переменную ниже. Если соответствия нет или оно неоднозначно,
не выбирать другой сертификат наугад. Окно выбора CryptoLite serial не показывает.

```powershell
$env:CRYPTOLITE_TEST_CERT_SERIAL = '<SerialForRunner разрешённого сертификата>'
$env:CRYPTOLITE_TEST_PDF = '<абсолютный путь к тестовому PDF>'
$env:CRYPTOLITE_TEST_OUTPUT_DIR = '<существующий каталог результатов>'
.\cryptolite-verification.exe --ignored --exact signer::pades::tests::real_pdf_signing --nocapture
```

Runner требует ровно одно совпадение serial без учёта регистра hex-букв, отвергает неоднозначность прямого и
обратного порядка его байтов в списке сертификатов, не выбирает первый сертификат
и не принимает thumbprint вместо backend ID. Создаёт уникальный `cryptolite-verify-*`,
проверяет direct и split/CAdES-BES маршруты, извлекает CMS по ASN.1 length и
подписываемое содержимое из **готовых PDF**, проверяет CMS и порчу байта каждого
из двух сегментов. Trust цепочки выводится отдельно. Ожидается один passed test;
ошибка или отсутствие сертификата не означает успешную приёмку.

Приёмка **именно переданной сборки** на внешнем ПК:

1. Зафиксировать SHA-256 exe и runner, версии Acrobat/КриптоПро PDF/CSP.
   Сначала проверить известный корректный PDF как контроль окружения.
2. В пустой output-каталог подписать исходный двухстраничный PDF через
   «Подписание → Штамп на PDF → Разместить штампы» на странице 2. В Acrobat:
   действительная подпись, нет ошибки ByteRange, обе страницы и штамп на выбранном месте.
3. Подписать ранее подписанный Acrobat PDF: обе подписи должны оставаться действительными.
4. Подписать двумя сертификатами за один запуск. Два последовательных запуска с одним
   сертификатом проверяют сохранение ревизий, но **не** закрывают UI multi-signer.
5. Повторить на синтетическом PDF с xref-table и на PDF с CRLF после EOF.
6. Открыть `direct.pdf` и `external.pdf` runner в Acrobat. Во вкладке «Проверка»
   выбрать извлечённые `*-signature.der` и соответствующие `*-content.bin`,
   detached=true, base64=false; ожидать valid=true. Сам PDF эта вкладка не проверяет.
   Оба `*-tampered-*.bin` с той же CMS должны отвергаться.
7. Проверить профиль новой CMS: detached id-data, contentType, messageDigest,
   signingCertificateV2 (либо допустимый signingCertificate); для ГОСТ-2012-256
   digest OID `1.2.643.7.1.1.2.2`. OpenSSL `cms -cmsout -print -inform DER -in <DER>`
   годится для просмотра ASN.1, но без GOST provider не доказывает подпись.
   Алгоритмы 512/2001 без подходящих разрешённых сертификатов отметить непроверенными.
8. Проверить прежние CMS attached/detached и CAdES-BES detached в DER/Base64,
   batch из двух неперсональных файлов. Источники не должны изменяться.

Для каждого сценария сохранить статус и текст ошибки без личных данных. Не публиковать
в PR пользовательские PDF, сертификаты, DER, содержимое, ключи или персональные скриншоты.
PR допускается только после локальной и внешней приёмки; hash-only проверка её не заменяет.

## Безопасность и лицензии

КриптоЛайт не является СКЗИ и не реализует криптографические алгоритмы: CMS/PKCS#7 формируется системным CryptoAPI с использованием установленного CryptoPro CSP. Для операций требуется установленный и лицензированный КриптоПро CSP. Библиотеки и материалы SDK КриптоПро в проект не включены. «КриптоПро» — товарный знак соответствующего правообладателя; проект не связан и не аффилирован с ним.

Приложение распространяется по Apache-2.0. Текущий проектный код предоставляется без гарантий в пределах лицензии. См. [LICENSE](LICENSE) и [NOTICE](NOTICE).
